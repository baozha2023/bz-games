BZ Games 游戏市场功能视频大纲与口播稿
====================================

建议成片时长：约 13—16 分钟

内容结构：
1. 市场功能与两级结构
2. 自建独立市场的完整流程
3. 向现有第三方市场加入一个游戏
4. MarketSource、MarketGame、MarketGameVersion 与 gameManifest 字段
5. 安装验证链路与投稿前自检

第 1 页｜把你的游戏放进游戏市场
大家好，这期视频单独讲 BZ Games 的游戏市场功能。我们不讲云同步，也不讲普通的本地导入，只解决一个问题：怎样把一个游戏正确地放进市场，让用户能看到、下载、校验并安装。视频会先解释两级市场结构，然后分别演示自建市场，以及只向现有第三方市场加入一个游戏，最后逐项讲清 market.json 中最容易写错的字段。

第 2 页｜市场负责发现与安装
这是用户实际看到的游戏市场。要先建立一个准确概念：market.json 并不保存游戏本体，它保存的是市场、游戏和版本的索引信息。真正的游戏文件仍然通过 downloadUrl 下载。平台拿到索引后，先展示市场和游戏，再根据版本对象完成下载、完整性校验、解压、清单校验与安装。后面所有 JSON 字段，都服务于这条链路。

第 3 页｜两级市场结构
BZ Games 采用两级市场结构。第一级是市场目录，读取 sources 数组，决定用户能看到哪些市场。第二级是某一个市场自己的索引，读取 games 数组。每个游戏下面再通过 versions 数组描述可安装版本。当前本地示例也验证了这一点：官方顶层 market.json 同时承担目录和自身市场索引，因此同时有 sources 和 games；第三方市场与 GitHub Release 市场则只有自己的市场索引。

第 4 页｜选择两条投稿路线
投稿前先选路线。路线 A 是单独建立一个市场，适合你要长期维护一组游戏，或者希望市场有独立品牌和分类。它最终需要作为一个 Source 注册到顶层目录。路线 B 是只加入一个游戏，适合大多数贡献者：找到定位合适的现有市场，只修改它的 games 数组并提交 PR。最常见的错误，就是为了加一个游戏又新建一个市场，或者在游戏 PR 里误改 sources。

第 5 页｜准备投稿材料
两条路线的共同前提，是先准备好游戏包和元数据。安装包支持 zip 与 7z。游戏 id 要用反向域名格式，版本号要符合语义化版本。还需要确定 downloadUrl、文件字节数和 SHA-256。最重要的硬约束是两组一致性：市场条目的 id 必须与包内 game.json.id 完全相同；版本对象的 version 必须与 game.json.version 完全相同。这里不一致，安装阶段一定会失败。

第 6 页｜自建市场步骤
自建市场按六步走。第一，创建独立仓库，并把 market.json 放在根目录。第二，定义市场身份。第三，在 games 中维护游戏。第四，发布安装包和展示素材。第五，在提交前做本地校验。第六，向顶层目录的 sources 数组注册这个市场。这里要分清职责：你自己的仓库维护 MarketIndex；顶层官方仓库只新增一个 MarketSource，告诉客户端去哪里找到你的 market.json。

第 7 页｜自建市场 JSON 骨架
这是外部独立市场最小骨架。schemaVersion 是索引格式版本；marketId 要稳定且唯一；marketName 是显示名称；generatedAt 和 updatedAt 使用 ISO 8601 时间；games 初始可以为空。注意，外部市场仓库通常不需要 sources，因为它只承担市场索引职责。本地第三方市场和 GitHub Release 市场的实际文件也是这种结构。只有顶层官方 market.json 同时承担目录职责，所以额外包含 sources。

第 8 页｜MarketSource 字段
把自建市场加入顶层目录时，需要新增一个 Source。它不复制游戏列表，只描述去哪里读取这个市场。repository 与 branch 决定 raw market.json 的位置；marketId 要与目标市场自己的 marketId 对齐；visibility 为 hidden 时不在市场列表展示；featured 控制重点推荐。coverUrl 是一级市场卡片封面。Source 的颗粒度是一个市场，不是一个游戏，所以不要为每个游戏新增 Source。

第 9 页｜向现有市场加入游戏
如果只是加入一个游戏，流程更短。先选择定位匹配的目标市场，例如第三方开源游戏市场，或者专门收录 GitHub Release Windows 包的市场。然后 Fork 目标仓库，在 market.json 的 games 数组中新增一个游戏对象，更新 updatedAt，完成校验后提交 PR。整个过程不需要修改顶层 sources，也不需要新建市场。PR 描述里最好写清游戏来源、许可证、入口文件和实际安装测试结果。

第 10 页｜MarketGame 最小示例
这是一个最小可用的游戏条目。Game 层描述游戏本身，Version 层描述一个具体安装包。必须至少有一个版本，而且 latestVersion 应该指向 versions 中的推荐稳定版本。示例里的 sha256 不能真的写提示文字，必须替换成 64 位十六进制摘要。对于普通非 GitHub Release 下载地址，当前代码要求提供 size，否则该版本不可下载。建议同时提供 sha256，把完整性校验闭环补齐。

第 11 页｜MarketGame 字段分组
Game 字段可以按职责分成四组。身份字段确定唯一性和作者；展示字段负责市场页面；分类字段决定游戏类型与玩家人数；发布字段控制推荐、可见性和版本集合。id 只能使用小写反向域名格式。name 和 author 最长 100 字符，summary 最长 200 字符。visibility 可以是 public、hidden 或 deprecated。多人类型建议提供人数范围，而实际 game.json 对 multiplayer 和 singlemultiple 会强制要求 multiplayer 配置。

第 12 页｜MarketGameVersion 字段与校验
Version 是最关键的下载对象。version 必须是有效 SemVer，platformVersion 必须是 SemVer 范围。downloadUrl 必须是 HTTP 或 HTTPS。sha256 可选，但只要填写就必须是 64 位十六进制。当前运行时代码还有一条明确规则：如果不是 GitHub Releases 的标准直链，缺少 size 就会判定为不可下载。GitHub Release 直链可以由平台尝试补充 size，但为了稳定，仍建议把 size 和 sha256 一起写全。

第 13 页｜game.json 与 gameManifest
清单有两种接入方式。第一种最推荐：安装包里直接带 game.json，平台在解压后读取并校验。第二种用于第三方包无法修改的情况：在对应 Version 下提供 gameManifest，平台会组合 Game 与 Version 的字段生成 game.json。gameManifest 不允许覆盖 id 和 version，这两个值分别来自 Game.id 与 Version.version。不要在包内清单和市场覆盖中重复维护两份相互冲突的配置。

第 14 页｜安装验证链路
平台不会拿到压缩包就直接运行。安装链路依次完成下载、size 与 SHA-256 校验、解压、清单校验、平台版本兼容检查，最后才安装。压缩包支持 zip 和 7z，game.json 可以位于根目录或第一层单子目录。路径安全也有严格限制：绝对路径、盘符路径、点目录和路径穿越都会被拒绝。讲这一页时可以提醒投稿者，JSON 能解析只代表第一关通过，真正的验收标准是完整走通安装。

第 15 页｜投稿前自检
提交前最后做一次自检。检查市场身份、反向域名 id、latestVersion 指向、版本号一致性、平台范围、下载地址、size 与 SHA-256。然后删除本机已经安装的同 id 同版本记录，用全新的状态再走一遍下载和安装。只有能从未安装走到可启动，才算完成投稿。如果是 PR，还要把测试平台版本、下载来源和入口文件写在描述里，方便维护者复核。

第 16 页｜三层职责总结
最后把整期视频压缩成三句话：一个市场对应一个 Source，一个游戏对应一个 Game，一个安装包对应一个 Version。大多数投稿者先走路线 B，只向现有市场加入一个游戏，成本最低也最容易验证。只有当你确实要长期维护一组游戏、需要独立名称和仓库时，再走路线 A 建立自己的市场。按照这三层职责拆分，market.json 就不会越写越乱。
