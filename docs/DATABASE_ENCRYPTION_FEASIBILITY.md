# 数据库加密可行性分析

> 版本：基于 BZ-Games v2.4.0  
> 日期：2026-06-10  
> 范围：仅分析可行性与改造方案，不包含代码修改  

---

## 一、结论

### 1.1 是否能加密

可以。

当前项目使用的是标准 `better-sqlite3`，数据库文件是普通 SQLite 文件，用户可以直接使用 Navicat、DB Browser for SQLite、sqlite3 CLI 等工具读取内容。

如果后续切换到支持加密的 SQLite 实现，例如 SQLCipher 或基于 `SQLite3MultipleCiphers` 的 `better-sqlite3` fork，那么数据库文件将不再是普通 SQLite 文件，未经密钥无法直接打开。

### 1.2 是否能达到"不让用户直接查看"的目标

可以达到，但要明确边界：

- **能防住**：普通用户直接打开 `.db` 文件查看内容。
- **不能完全防住**：有本机权限、会逆向 Electron 程序、会抓取运行时密钥的高级用户。

因此，这类方案的本质是：

> **提升门槛，防止直接查看，而不是实现绝对不可见。**

## 二、当前项目现状

### 2.1 当前数据库接入方式

当前主进程直接使用标准 `better-sqlite3` 打开数据库：

- [DatabaseService.ts:L26-L53](file:///f:/IDEA/idea-workspace/bz-games/src/main/services/storage/DatabaseService.ts#L26-L53)
- [package.json:L27-L47](file:///f:/IDEA/idea-workspace/bz-games/package.json#L27-L47)

现有特征：

- 使用本地 SQLite 文件存储游玩会话记录
- 未配置任何数据库密钥
- 未执行 `PRAGMA key` / `rekey` 等加密初始化
- 已启用 `journal_mode = WAL`

因此，当前数据库属于**明文 SQLite 文件**。

### 2.2 当前实现的优点

- 架构简单
- 查询性能高
- 与 `better-sqlite3` API 完全兼容
- 打包方案已适配原生模块

### 2.3 当前实现的缺点

- 用户只要找到数据库文件就能直接浏览
- 备份、复制、发送数据库文件后，第三方也能直接读取
- 对"本地敏感数据不可见"这一目标没有任何保护

## 三、可行方案对比

### 3.1 方案 A：切换到 `better-sqlite3-multiple-ciphers` 或同类加密 fork

这是当前项目最现实的方案。

该类库保持了与 `better-sqlite3` 接近的 API 形式，但底层接入了加密版 SQLite，可通过密钥打开数据库文件。

参考：

- https://www.npmjs.com/package/better-sqlite3-multiple-ciphers

#### 优点

- 与当前技术栈最接近
- 迁移成本相对可控
- 仍可保留 SQLite 的查询能力与表结构
- 可直接实现"普通工具无法裸打开数据库"

#### 风险

- 原生模块需重新验证 Electron 版本兼容性
- 数据库初始化流程要调整
- 明文旧库需要迁移到加密库
- 需要处理密钥管理问题

#### 结论

**推荐优先评估此方案。**

---

### 3.2 方案 B：使用 SQLCipher

SQLCipher 是 SQLite 的成熟加密方案，可对整个数据库文件进行透明加密。

参考：

- https://github.com/sqlcipher/sqlcipher

#### 优点

- 方案成熟
- 社区资料较多
- 数据库整体加密，安全语义明确

#### 风险

- Node/Electron 下通常仍需通过特定绑定或 fork 落地
- 集成方式未必比方案 A 更轻
- 需要额外验证与当前 Electron 打包链路的兼容性

#### 结论

如果选型上最终仍落到 `better-sqlite3` 兼容 fork，本质上会与方案 A 接近。

---

### 3.3 方案 C：使用 SQLite SEE

SQLite SEE 是 SQLite 官方提供的加密扩展。

参考：

- https://www.sqlite.org/see/doc/trunk/www/readme.wiki

#### 优点

- 官方加密扩展
- 与 SQLite 体系契合度高

#### 风险

- **商业授权**
- 集成和交付复杂度高于开源路线
- 对当前开源项目并不一定划算

#### 结论

除非明确接受授权成本，否则不建议优先考虑。

---

### 3.4 方案 D：自行对数据库文件做外层加密

例如应用关闭后手动加密 `.db` 文件，启动时再解密。

#### 问题

- 会破坏 SQLite 正常读写体验
- 与 `WAL`、`-shm`、`-wal` 文件协同复杂
- 崩溃恢复、并发访问、异常退出场景容易出错
- 工程复杂度高，收益低

#### 结论

**不推荐。**

## 四、关键技术问题

### 4.1 密钥存在哪里

这是数据库加密真正的核心问题。

如果只是把密钥硬编码在代码里，那么虽然普通用户无法直接用 Navicat 打开数据库，但仍然可能通过以下方式拿到密钥：

- 逆向安装包或源码
- 调试主进程
- 注入运行时并读取内存

因此，密钥方案至少要考虑以下几种：

#### 方案 1：硬编码在应用中

- 优点：实现简单
- 缺点：安全性最弱
- 适用：只追求"别让普通用户顺手打开"

#### 方案 2：使用 Windows DPAPI / Credential Manager 保存密钥

- 优点：更符合桌面应用习惯
- 缺点：仍然不是绝对安全
- 适用：当前 Windows-only 项目，现实性较高

#### 方案 3：让用户设置主密码

- 优点：安全上限更高
- 缺点：产品体验更复杂，涉及忘记密码、重置密码、首次引导
- 适用：确实存在较强隐私需求的产品

#### 建议

对于当前 BZ-Games，若目标只是避免数据库被普通用户直接查看，建议优先考虑：

> **系统安全存储 + 应用自动解锁**

也就是使用系统级凭据能力保存数据库密钥，而不是让用户每次手动输入。

---

### 4.2 旧数据库如何迁移

当前线上用户如果已经存在明文数据库，切换到加密方案时必须处理迁移。

典型流程如下：

1. 启动应用
2. 检测现有数据库是否为明文
3. 若为明文，则创建加密数据库
4. 将数据迁移到新库
5. 校验迁移结果
6. 备份旧库或安全删除旧库

这里的风险点包括：

- 应用中途中断导致迁移不完整
- 迁移失败后回滚策略不明确
- WAL 文件残留
- 用户机器上已有损坏数据库时的容错处理

因此，迁移必须作为一个单独设计项，而不是附带实现。

---

### 4.3 与 WAL 的兼容性

当前数据库初始化时启用了 WAL：

- [DatabaseService.ts:L34-L35](file:///f:/IDEA/idea-workspace/bz-games/src/main/services/storage/DatabaseService.ts#L34-L35)

WAL 对性能有帮助，但在引入加密后需要特别关注：

- 加密库是否支持当前 WAL 使用方式
- 新建加密库与打开已有加密库时的初始化顺序
- 数据库升级时是否需要临时切换 journal 模式
- 异常退出后 WAL 回放是否稳定

这不是不能做，而是需要在落地阶段重点验证。

## 五、对 Navicat 的实际效果

如果数据库切换为加密 SQLite：

- Navicat 无法像普通 SQLite 一样直接打开文件
- DB Browser for SQLite 也无法直接读出数据
- sqlite3 CLI 直接执行查询通常会报错或识别失败

换句话说，用户看到的体验会是：

> 这个数据库文件存在，但不是可直接读取的普通 SQLite 文件。

这正好符合当前需求：

> **不要让用户直接通过 Navicat 查看。**

## 六、安全边界说明

数据库加密能够解决的是**静态文件暴露**问题，而不是所有本地攻击问题。

### 6.1 能防住什么

- 用户直接双击数据库文件查看
- 通过 Navicat / SQLite 浏览器直接读取
- 拷走数据库文件后在另一台机器上直接查看
- 普通层面的数据泄露

### 6.2 防不住什么

- 本机管理员级别攻击
- 运行时内存抓取
- 对 Electron 主进程的调试与注入
- 通过修改程序逻辑绕过读取限制

因此，数据库加密的正确定位应当是：

> **本地静态数据保护，而不是强对抗安全方案。**

---

## 七、推荐路线

### 7.1 推荐结论

建议优先采用以下路线：

1. 保持 SQLite 架构不变
2. 将标准 `better-sqlite3` 评估替换为支持加密的兼容 fork
3. 使用系统安全存储保存数据库密钥
4. 设计一次性的明文库迁移流程
5. 对 WAL、打包、升级进行专项验证

### 7.2 为什么推荐这条路线

- 对现有业务代码侵入相对最小
- 不需要推翻当前统计与查询逻辑
- 能直接满足"别让用户用 Navicat 直接查看"这一目标
- 工程复杂度可控

### 7.3 不推荐的路线

- 不推荐自行封装文件级加密
- 不推荐只做表字段级加密后仍保留明文 SQLite 结构
- 不推荐把密钥明文硬编码后误以为已经获得高强度安全

## 九、最终结论

### 可行性判断

**可行。**

### 是否值得做

如果当前目标是：

> 不让普通用户直接用 Navicat 或类似工具查看本地数据库内容

那么这项改造是**值得做**的，且能带来明确收益。

### 需要注意的核心事实

- 数据库加密可以防止直接查看数据库文件
- 数据库加密不能防止高权限运行时攻击
- 真正的难点不在"是否能加密"，而在"密钥如何保存"与"旧数据如何迁移"

### 最终建议

> **建议进入技术设计阶段，优先验证 `better-sqlite3` 兼容加密方案 + 系统密钥存储的组合路线。**
