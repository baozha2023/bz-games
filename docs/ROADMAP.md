# BZ-Games 未来版本规划

> 当前版本：**v3.1.1** | 最后更新：2026-07-28

---

## 架构原则：服务器是边缘性的

BZ-Games 的核心理念是**本地优先**。官方 Relay Server 仅提供以下边缘能力：

| 能力              | 说明                                       | 离线时的影响                                           |
| :---------------- | :----------------------------------------- | :----------------------------------------------------- |
| 房间中继          | 帮助无法直连的玩家通过公网中转联机         | LAN / frp 直连完全不受影响                             |
| GitHub OAuth 登录 | 云端同步功能的身份认证入口                 | 所有本地功能（游戏库、成就、统计、经济系统）均无需登录 |
| 云端文件同步      | config.json + SQLite 数据的远程备份        | 不影响本地使用，数据始终以本地为准                     |
| 建言献策          | 接收可选文字和图片，供项目维护者查看与处理 | 不影响平台及游戏功能                                   |

**核心约束**：任何主要功能都不能依赖服务器。以下规划中的所有特性均遵循此约束——功能在离线环境必须完整可用，云端能力仅作为可选的增强补充。

## 版本策略

BZ-Games 采用 **渐进式版本演进** 策略，每个大版本聚焦一个核心主题：

| 版本     | 代号     | 主题             | 预计跨度 |
| :------- | :------- | :--------------- | :------- |
| **v3.1** | _Refine_ | 体验打磨与稳定性 | 1-2 个月 |
| **v3.2** | _Social_ | 本地社交与分享   | 2-3 个月 |
| **v3.5** | _Cross_  | 跨平台扩展       | 3-5 个月 |
| **v4.0** | _Studio_ | 创作者生态       | 4-6 个月 |

## v3.1 — Refine（体验打磨与稳定性）

### 目标

在 v3.0 的稳定架构之上，打磨细节体验，提升性能与可靠性。

### 3.1.0 核心特性

#### 1. 性能优化 — 大型游戏库

**现状**：游戏库超过 100 个游戏时，封面加载可能出现卡顿。

**方案**：

- 游戏封面图片懒加载（基于现有 `CachedImg` 组件增强）
- 库视图虚拟滚动，减少 DOM 节点数
- 大型游戏库搜索增加防抖
- `getGamesList()` 按需分页

**依赖**：无外部依赖，纯前端优化。

#### 2. 手柄支持增强

**现状**：平台不做手柄映射，完全依赖游戏自行处理。

**方案**：

- 设置页新增全局手柄配置：按键映射、振动强度、死区设置
- 通过 HTML5 Gamepad API 在 Web 游戏中提供统一手柄输入
- 配置本地存储，离线可用

**依赖**：Electron 原生支持 Gamepad API，无需额外库。

#### 3. 市场详情页增强

**现状**：市场游戏详情已展示基础信息、版本列表、封面和下载进度。

**方案**：

- 版本更新日志（Release Notes）Markdown 渲染展示
- 「相关游戏」推荐（基于标签/分类匹配）
- 下载队列并行数可配置

**依赖**：`MarketGameVersionSchema` 已有 `releaseNotes` 字段，仅需 UI 层面增强。

#### 4. 数据库加密

**现状**：本地 `bz_games.db` 已使用 `better-sqlite3-multiple-ciphers` 和 ChaCha20 加密，游戏实体、会话、成就与统计事件统一存储。

**已完成**：

- 数据库连接统一使用 `better-sqlite3-multiple-ciphers`。
- 构建私有配置中的固定种子经 SHA-256 派生数据库密钥。
- 正式旧版配置与三库布局一次性迁移到加密统一库。
- 云同步只导出业务表的明文 SQL，不上传游戏实体和本地加密库文件。

#### 5. 数据健康自动修复

**现状**：`healthCheck()` 仅上报问题（如游戏目录缺失、game.json 丢失），不做自动清理。

**方案**：

- 启动时自动运行健康检查，对于确认不可恢复的问题（如版本目录物理删除）自动清理对应 GameRecord 条目
- 对可恢复问题（如 game.json 暂时不可读）仅告警不删除
- 清理前的 SQLite 游玩记录可选择保留或级联删除

**依赖**：`StoreService.healthCheck()` 已有完整的检测逻辑，仅需增加修复动作。

## v3.2 — Social（本地社交与分享）

### 目标

在局域网和本地层面构建社交能力，不依赖任何服务器。

### 3.2.0 核心特性

#### 1. LAN 好友系统

**方案**：

- 基于现有 `LocalNetworkService`（UDP 广播发现）扩展好友发现
- 好友列表存于本地 `config.json`，含玩家 ID、昵称、备注
- 同一局域网内的好友自动显示在线状态
- 好友间可通过 LAN 直连发送文字消息（不走 Relay）
- 好友快捷邀请加入房间

**关键约束**：好友列表完全本地存储，在线发现完全基于 LAN UDP。不通过 Relay Server 中转任何好友数据。

#### 2. LAN 游戏分享

**方案**：

- 好友间通过 LAN TCP 直连传输游戏安装包
- 发送方选择游戏版本，接收方确认后开始传输
- 接收方自动校验 SHA256（使用市场索引中的校验值，或发送方计算）
- 传输进度在通知中心展示
- 传输完成后自动导入到游戏库

**可行性**：已有 `LocalNetworkService`（UDP 广播发现），可扩展 TCP 直连通道用于文件传输。

#### 3. 游戏截图管理

**方案**：

- 全局快捷键截图（默认 `Ctrl+Shift+S`），自动保存到本地截图目录
- 截图按游戏 ID 自动分组
- 截图管理器：浏览、删除、复制、打开文件夹
- 游戏中成就解锁时自动截图（可选开关）

**依赖**：Electron 的 `BrowserWindow.capturePage()` + `desktopCapturer`。纯本地功能，无服务端依赖。

#### 4. 本地活动回顾

**方案**：

- 首页可选「动态回顾」面板（基于本地数据生成，可折叠）
  - 「今天玩了 X 款游戏，总计 Y 小时」
  - 近期解锁的成就展示
  - 「N 天前你第一次玩了某某游戏」
  - 市场有游戏更新提醒（拉取市场索引时检查本地已安装游戏的版本）
- 所有数据来源于本地 SQLite + config.json，不依赖任何远程推送

**可行性**：成就弹窗体系已完善，SQLite 中有完整的游玩和成就历史数据源。

## v3.5 — Cross（跨平台扩展）

### 目标

打破 Windows 桌面端边界，让 BZ-Games 覆盖更多平台。

### 3.5.0 核心特性

#### 1. macOS 与 Linux 支持

**方案**：

- 主进程平台相关代码用策略模式分离（文件路径、窗口管理、托盘）
- macOS：.app 打包、DMG 分发
- Linux：AppImage / Flatpak / deb 打包
- 7z 解压使用各平台对应二进制（`7zip-bin` 已支持跨平台）
- 窗口管理适配各平台托盘、菜单、快捷键规范

**可行性**：Electron 本身跨平台，当前 `better-sqlite3-multiple-ciphers` 原生模块需要分别验证 macOS、Linux 与 Windows 的编译、签名和打包。

#### 2. LAN 伴侣 App

**方案**：

- 移动端/其他设备上的轻量 App（React Native / Capacitor），不是完整游戏平台
- 核心功能：
  - 通过 LAN 连接桌面端，查看本地游戏库、成就、统计
  - 接收桌面端的房间邀请通知（LAN 推送）
  - 远程触发桌面端下载队列
- 与桌面端在同一局域网内直连通信，不走任何外网服务器

**关键约束**：伴侣 App 仅通过 LAN 与桌面端通信，Relay Server 不是通信通道。

#### 3. Web 版轻量启动器

**方案**：

- 纯 Web 版 BZ-Games（浏览器运行），作为市场浏览和 light 体验入口
- 仅支持 `networkgame` 类型游戏（直接 URL 启动）
- 不支持本地游戏导入和联机房间（浏览器限制）
- 市场浏览、游戏详情查看功能完整

**可行性**：App 路由系统已是标准 Vue 3 SPA，独立构建部署即可。

## v4.0 — Studio（创作者生态）

### 目标

从游戏消费平台升级为游戏创作与分发平台，所有创作工具本地运行。

### 4.0.0 核心特性

#### 1. 游戏项目模板与脚手架

**方案**：

- 内置多种游戏模板（平台跳跃、消除、棋牌等），一键创建项目
- 自动生成符合规范的 `game.json` 和基础代码结构
- 模板项目开箱即用 Game API 连接，可直接在平台内调试
- 支持从模板导出为标准游戏包

**依赖**：完全本地工具链，不依赖任何在线服务。

#### 2. 创作者工坊（市场扩展）

**方案**：

- 利用现有市场体系（第三方市场源），允许用户发布自制游戏
- 工坊本质上是一个社区维护的 GitHub 仓库作为市场源
- 游戏审核通过 GitHub PR + Actions 自动化流程
- 用户从工坊安装游戏与从市场安装流程完全一致

**可行性**：市场体系已有二级架构（市场目录 + 市场索引），工坊是市场体系的自然扩展。

#### 3. MOD 系统

**方案**：

- 游戏在 `game.json` 中声明 `modSupport: true`
- MOD 格式：`.bzmod` 归档包，包含覆盖文件和 `mod.json` 清单
- 本地 MOD 管理面板：启用/禁用/排序，支持冲突检测
- MOD 加载：在游戏启动时将启用的 MOD 文件覆盖到游戏目录

**可行性**：`GameEnvironment` 负责游戏文件管理，MOD 加载本质是文件覆盖层，完全本地操作。

## 架构演进原则

1. **渐进增强，不破坏**：新版本必须向后兼容旧版本游戏包和 API
2. **服务器是边缘的**：核心体验不依赖任何服务器，云端功能始终是可选的附加增强
3. **用户数据主权**：用户数据始终存储在本地，云端同步需用户主动授权
4. **轻量高内聚**：避免依赖臃肿，保持安装包 < 200MB
5. **开放标准**：游戏包格式、Game API 协议均文档化并开放
