# BZ-Games 未来计划

最后更新：2026-08-26

规划基线：`v3.4.2`

本文描述 BZ-Games 从当前平台继续演进的方向、顺序和验收标准。它不是功能许愿清单，也不承诺固定发布日期。阶段顺序代表依赖关系：只有上一阶段形成稳定闭环，下一阶段才进入主要开发。

已经完成的能力只作为规划基线，不再混入未来事项；实验性方向必须先通过用户价值、维护成本、安全边界和降级方案评审，才能进入版本计划。

## 一、产品定位

BZ-Games 不是在线商店的轻量复制品，也不以替代所有游戏平台为目标。它首先是属于玩家自己的本地游戏平台，同时为独立游戏提供分发、联机、社区和创作者工具。

平台希望形成四个彼此独立、又可以自然连接的闭环：

1. **本地游玩闭环**：导入或安装游戏，可靠启动、管理版本、记录生涯，并能恢复数据。
2. **内容分发闭环**：从开放市场发现游戏，验证资源，原子安装、更新或回退。
3. **联机闭环**：游戏只接入统一 Game API，即可获得房间、聊天、中继、状态同步和断线恢复能力。
4. **社区与创作闭环**：玩家围绕游戏交流，创作者提交和维护作品，平台提供审核、治理与运维工具。

GitHub 登录、在线状态、官方 Relay、论坛和托管市场都是增强能力，而不是本地游戏库和单机游玩的通行证。任何在线模块不可用时，玩家仍应能够管理和启动已安装的本地游戏。

## 二、当前平台基线

截至 `v3.4.2`，平台已经具备以下可继续建设的基础。

### 2.1 本地客户端

- Windows 10/11 x64 桌面客户端，基于 Electron、Vue 3 和 TypeScript。
- 多游戏库路径、多版本共存、异步导入、任务恢复、收藏、排序和多种库布局。
- Native、Web、本地服务和 URL 等启动模式，以及统一的进程树和窗口生命周期管理。
- 加密 SQLite、加密配置、本地游戏清单、游玩会话、统计、成就和游戏生涯。
- 最终 NSIS 更新前快照恢复、`.bzgames` v1 手工迁移导出、缓存清理、数据自检和安全卸载。
- 头像、头像框、昵称样式、游戏卡片、BZ 币和签到等本地个性化能力。
- 简体中文、繁体中文、English、日本語、Deutsch 五种语言。

### 2.2 市场与创作者链路

- 官方市场、GitHub Release 市场和第三方市场组成的多来源目录。
- ZIP/7z 下载、大小与 SHA-256 校验、断点续传、暂停、恢复、取消和中断恢复。
- 暂存目录与原子安装，市场来源、游戏 ID 和版本来源可追踪。
- Relay 托管游戏的元数据、版本、安装包、封面、图标、审核、发布和删除流程。
- 玩家、创作者、管理员、超级管理员的服务端 capability 授权边界。

### 2.3 联机与 Game API

- 局域网、用户自备公网入口和官方 Relay 三种连接路径。
- 房间发现、创建、加入、准备、开始、离开、踢人、解散、密码和断线重连。
- 文字、语音、图片聊天，以及游戏消息中继和可靠确认。
- Game API V1 JSON 协议与 V2 二进制增强协议。
- 房主进程生命周期驱动的全房间游戏开始和结束语义。

### 2.4 在线身份与社区

- GitHub OAuth 登录、会话生命周期、用户昵称、在线状态和最后在线时间。
- 平台数据不提供云端快照；V2 本地备份负责完整导入导出，账号凭据不进入归档。
- 登录用户反馈、图片、历史记录、官方回复和状态跟踪。
- 论坛信息流、搜索、游标分页、富文本正文、图片、点赞、评论和作者删除。
- 论坛游戏提及、服务端敏感词过滤、限流、软删除、管理员治理和搜索 outbox。
- Elasticsearch 为可选搜索增强；不可用时不影响最新帖子、发帖和评论。

### 2.5 发布与运维

- 独立 Relay Server、同源管理端、MySQL、MongoDB 和可选 Elasticsearch。
- 反馈、论坛、用户、托管游戏、平台版本和系统监控的管理入口。
- GitHub Actions 与超级管理员上传共用桌面版本校验和原子发布程序。
- 服务端测试、权限矩阵、带宽限制、发布锁、健康信息和生产部署文档。

## 三、设计原则

所有未来功能都必须服从以下原则。无法满足时，默认选择不做或缩小范围。

### 3.1 本地优先，而不是仅做离线缓存

- 本地游戏库、游戏启动、成就、统计和基础设置不要求登录。
- 在线状态不能成为本地数据的唯一事实来源。
- 云端恢复必须合并到本地，而不是不透明地覆盖玩家数据。
- 平台退出在线服务后，玩家仍能保有可理解、可迁移的数据。

### 3.2 在线增强必须可降级

- Relay 不可用时保留局域网和自备公网入口。
- 搜索不可用时保留论坛时间流。
- 社区不可用时保留市场浏览、安装和本地游玩。
- 单个市场源失败不能拖垮其他来源。
- 降级状态要明确展示，不能伪装成空数据。

### 3.3 玩家拥有选择权

- 市场保持多来源，不将官方托管设为唯一安装路径。
- 不引入强制 DRM、在线所有权验证或启动前联网检查。
- V1 导入、V2 备份、在线状态和未来通知均应提供清晰入口、状态与退出路径。
- 删除、迁移、导入和覆盖前必须说明影响并提供恢复路径。

### 3.4 服务端只信任可验证事实

- 客户端提交的用户 ID、角色、市场来源和资源归属只能作为提示，不能作为授权依据。
- 认证、资源所有权、角色能力、限流和状态机由服务端验证。
- 文件同时校验路径边界、类型、签名、大小、哈希和内容结构。
- 凭据只注入经过精确协议、origin 和路径校验的请求。

### 3.5 原子操作和可恢复失败优先

- 导入、安装、同步、更新和发布都先写暂存区，再原子切换。
- 中断后要么恢复任务，要么回到操作前状态，不留下看似完整的半成品。
- 数据库结构变化必须先备份、验证生产结构并准备可审核的恢复步骤。
- 同版本、同内容应幂等成功；同版本、不同内容必须返回明确结果，不静默替换当前文件。

### 3.6 平台能力保持正交

- 游戏运行、联机、市场、社区和账号通过稳定接口组合，不互相侵入核心状态。
- 论坛是社区内容主干，不再为每个场景复制一套帖子、评论和审核系统。
- Game API 通过能力协商演进，避免游戏绑定单一客户端版本。
- 管理端按 capability 展示入口，服务端仍是唯一授权来源。

### 3.7 小闭环先于大生态

- 每个阶段先解决一条完整用户路径，再扩展点赞、推荐、关系链等外围能力。
- 不用功能数量衡量进展，优先减少失败率、恢复成本和理解成本。
- 新增服务前先判断能否复用现有 Relay、MySQL、MongoDB 和任务基础设施。

## 四、规划目标与衡量方式

### 4.1 北极星目标

让玩家可以长期、可靠地管理自己的游戏与数据，让创作者以最低接入成本获得分发、联机和社区能力，同时不把任何一方锁定在必须持续在线的中心服务中。

### 4.2 核心衡量维度

| 维度       | 希望改善的结果                             | 不采用的替代指标               |
| ---------- | ------------------------------------------ | ------------------------------ |
| 本地可靠性 | 导入、启动、退出、更新和恢复路径可重复验证 | 单纯统计页面或按钮数量         |
| 分发可信度 | 资源来源清晰，校验完整，失败可恢复         | 用下载量掩盖安装失败           |
| 联机可用性 | 房间状态一致，异常断线可理解、可恢复       | 只记录连接建立次数             |
| 社区质量   | 有效讨论能够被发现，违规内容可以治理       | 追求无边界的发帖增长           |
| 创作者效率 | 从清单校验到发布审核的步骤更少、更明确     | 只增加更多表单字段             |
| 运维质量   | 部署可验证、可回滚，故障影响范围可控       | 以服务进程仍在运行代替健康检查 |

平台不以引入持续行为追踪为路线图前提。需要度量时，优先使用本地可见诊断、匿名聚合运行指标和用户主动提交的故障信息。

## 五、阶段一：可信运行基线

这是所有后续功能的最高优先级。目标不是继续增加入口，而是让已有链路具备稳定交付和长期维护能力。

### 5.1 客户端可靠性

- 为真实旧版本数据库补齐升级、恢复和重复执行测试。
- 覆盖多游戏库迁移、空间不足、文件占用、符号链接和跨盘失败场景。
- 统一 V1/V2 导入、V2 导出、市场安装和游戏库迁移的任务状态与恢复语义。
- 建立游戏运行状态、房间状态和客户端重启后的对账机制。
- 将数据自检结果扩展为可导出的脱敏诊断报告。

### 5.2 服务端和数据

- 为 MySQL、MongoDB、GridFS 和 Elasticsearch 建立备份、恢复与一致性检查清单。
- 所有生产结构变化附带目标结构、手工 SQL、历史数据处理、验证查询和回退说明。
- 清理论坛搜索 outbox、过期会话、限流 reservation 和孤立对象时保留可审计结果。
- 为关键写操作补齐并发、幂等、超时和部分失败测试。
- 统一受保护接口的稳定错误码、HTTP 状态和用户可读消息。

### 5.3 发布与可观测性

- 固化 Relay、管理端和桌面版本的一致部署入口。
- 部署前验证配置与依赖，部署后执行全量测试、进程检查和真实 HTTP/WebSocket 健康检查。
- 保留自动回滚路径；只有新版本验证通过后才删除备份。
- 对数据库、对象存储、搜索、房间、下载和外部 GitHub 请求分别展示健康状态。
- 日志使用稳定事件名和关联 ID，避免记录令牌、Cookie、完整隐私内容和真实本地路径。

### 5.4 阶段验收

- 无网络环境下，本地导入、启动、统计、成就和设置仍可用。
- 全新安装、旧数据升级、任务中断和恢复均有自动化验证。
- 服务端可在一套明确流程中完成部署、验证和回滚。
- 可选依赖故障不会阻断无关功能，并能在界面上区分“无数据”和“服务不可用”。
- 客户端、Relay 和管理端全量测试可由统一命令稳定执行。

## 六、阶段二：社区质量闭环

论坛已经承担社区主干，下一阶段重点是让内容可持续，而不是立即扩张为完整社交网络。

### 6.1 内容治理

- 完成帖子、评论、图片、用户和处理记录的一体化管理视图。
- 增加用户举报入口、举报原因、重复举报合并和处理状态。
- 明确作者删除、管理员隐藏、超级管理员恢复和永久清理之间的语义。
- 对被限流、被过滤、被隐藏和搜索不可用分别给出可理解反馈。
- 建立社区规则、图片规则、申诉入口和管理员操作审计。

### 6.2 游戏讨论，而不是平行评论系统

- 复用论坛中的结构化游戏提及，形成按 `market_id + game_id + game_version` 聚合的讨论入口。
- 市场详情页展示相关讨论摘要，并可带游戏上下文进入发帖页。
- 手动导入或来源未知的游戏可以浏览公共讨论，但不能伪造已验证的市场版本身份。
- 首期不单独建设一套市场评论表、点赞和审核后台，避免社区数据割裂。
- 只有在论坛讨论模型无法满足简短评价场景时，再评估独立评分或评论模型。

### 6.3 最小通知闭环

- 提供回复、被提及、帖子处理结果和反馈回复通知。
- 通知使用有限保留期、游标分页和已读状态，不无限积累。
- 客户端允许关闭在线通知，关闭后不影响论坛主动浏览。
- 第一阶段不加入陌生人私信和群聊，降低骚扰与审核成本。

### 6.4 阶段验收

- 玩家可以从市场进入相关讨论，再从帖子返回对应游戏或版本。
- 每类社区写操作都有所有权、限流、举报、管理和审计路径。
- Elasticsearch 停止时，时间流、详情、发帖和评论仍正常工作。
- 通知失败不会影响原始业务操作，重复投递不会产生重复未读项。

## 七、阶段三：创作者到玩家的分发闭环

目标是让“制作完成”到“玩家可靠安装”的全过程更清楚、更少人工排错。

### 7.1 创作者工具

- 提供可视化 `game.json` 编辑、Schema 校验和入口预览工具。
- 提供 Game API 本地调试面板，模拟认证、房间玩家、消息、统计和成就事件。
- 发布前检查文件结构、符号链接、平台兼容范围、资源大小和入口可启动性。
- 生成可分享的校验报告，确保创作者与审核员看到同一结果。

### 7.2 托管与审核

- 增加草稿、待审核、已发布、已弃用之间明确的版本状态机。
- 展示版本变更说明、审核记录、驳回原因和重新提交历史。
- 对替换文件、调整最新版和删除资源增加影响分析与二次确认。
- 创作者只能管理自己的作品；管理员审核内容，超级管理员处理平台级例外。
- 审核通过的资源与导出市场索引进行自动一致性检查。

### 7.3 市场安装与更新

- 明确展示来源、发布者、版本、更新时间、校验状态和平台兼容性。
- 为已安装游戏提供可预览的更新差异、更新说明和保留旧版本选项。
- 安装失败保留可诊断状态；重试复用可信缓存，不重复下载已验证内容。
- 建立跨市场重复 ID、失效下载地址、哈希漂移和索引滞后的自动检查。
- 对第三方来源维持同一安全校验，但不暗示平台为其内容背书。

### 7.4 阶段验收

- 一个新游戏可以在不手改 JSON 的情况下完成校验、提交、审核、发布和安装。
- 审核结果、市场索引和真实下载资源不存在静默不一致。
- 同一安装任务在暂停、崩溃和重启后不会产生重复版本或半成品目录。
- 玩家始终能够判断游戏来自哪里、安装了什么、校验是否完整。

## 八、阶段四：本地内容与数据主权

这一阶段继续强化 BZ-Games 与纯在线平台的差异：玩家的数据和内容首先属于玩家。

### 8.1 存档与快照

- 支持按游戏配置存档目录，并建立本地手动快照。
- 快照包含来源版本、创建原因、文件数量、大小和完整性摘要。
- 恢复前自动保存当前状态，避免一次错误恢复覆盖唯一副本。
- 云端存档仅作为显式选择的增强能力，不默认上传，也不与平台数据快照混为一体。

### 8.2 截图与生涯

- 提供按游戏归档的截图管理、查看、导出和删除能力。
- 可选在成就解锁时截图，并允许逐游戏关闭。
- 将版本、会话、成就、统计和截图组合为可导出的本地生涯摘要。
- 分享产物只包含用户确认的内容，不附带本地路径、账号令牌或隐私元数据。

### 8.3 启动配置

- 支持每个游戏维护多个启动配置，包括版本、参数、环境变量和窗口偏好。
- 清楚区分平台管理参数、游戏自定义参数和敏感环境变量。
- 启动配置可本地导入导出，但敏感字段默认排除。

### 8.4 阶段验收

- 存档备份和恢复具备中断保护、完整性验证和恢复前快照。
- 截图和生涯数据可以完全离线管理并独立导出。
- 删除游戏前能够明确选择是否保留存档、截图和生涯记录。
- 云端服务不可用不会阻止任何本地备份和恢复操作。

## 九、阶段五：好友、在线状态与邀请

好友页当前仍是占位能力。只有社区治理、通知和在线状态稳定后，才进入关系链建设。

### 9.1 关系和隐私

- 好友请求必须双向确认，支持拒绝、删除和屏蔽。
- 在线状态默认遵循现有用户开关，并增加“所有人、好友、仅自己”等可见范围。
- 备注只保存在备注创建者一侧，不向对方公开。
- 明确关系数据、邀请记录和最后在线时间的保留期限。

### 9.2 房间邀请

- 从好友列表邀请进入现有房间，不复制第二套房间状态。
- 邀请只携带服务器可验证的房间定位信息，不暴露本地地址和凭据。
- 加入前继续执行本地游戏、版本、密码和房间容量检查。
- 对离线、拒绝、过期、房间结束和版本不兼容分别返回状态。

### 9.3 阶段边界

- 首版不提供陌生人私信、群组、动态广场或无限离线消息。
- 不将好友数量、在线时长或签到转化为竞争性排名。
- 不为了好友功能强制开启在线状态或持续后台运行。

### 9.4 阶段验收

- 好友关系和屏蔽关系在并发请求下保持一致。
- 用户关闭在线状态后，客户端和服务端都不再向无权查看者暴露状态。
- 房间邀请失败不会改变现有房间状态，也不会阻断手动加入。

## 十、阶段六：Game API 与开发者生态

Game API 是平台长期差异化能力。未来演进重点是稳定契约和开发体验，而不是无边界扩张接口数量。

### 10.1 协议稳定性

- 为 V1/V2 建立版本化兼容矩阵和协议一致性测试套件。
- 所有增强能力通过认证响应中的 capability 协商，未知能力默认忽略。
- 补齐断线、重复消息、乱序、超时、背压和大帧限制测试。
- 明确废弃流程：先标记、提供替代方案、跨稳定版本保留兼容，再删除。

### 10.2 SDK 与模板

- 提供最小 JavaScript/TypeScript SDK，封装认证、请求关联、重连和错误码。
- 提供 Native 与 Web 最小示例游戏，覆盖单机、房间消息、统计和成就。
- 提供协议录制与回放工具，帮助复现联机问题。
- 开发者工具只连接本机受控端口，不开放任意远程调试入口。

### 10.3 文档与认证

- 开发者指南、共享类型、服务实现和示例必须由一致性检查约束。
- 为游戏包提供“兼容 BZ-Games”校验报告，而不是付费或封闭认证。
- 兼容性标识只说明通过了哪些自动检查，不代表内容质量或安全背书。

### 10.4 阶段验收

- 示例游戏可以只依赖公开文档和 SDK 完成接入。
- 客户端升级不会让声明兼容的现有游戏静默失效。
- 协议故障可以通过脱敏录制、关联 ID 和本地模拟稳定复现。

## 十一、持续工程工作

以下工作不属于某一个版本，必须贯穿全部阶段。

### 11.1 安全与隐私

- 持续审计 IPC、路径、压缩包、富文本、图片、URL 跳转和凭据注入边界。
- 管理写操作必须保留 capability、精确 Origin、资源归属和审计记录。
- 客户端日志、服务端日志和诊断导出默认脱敏。
- 新增数据字段时同步说明用途、保存位置、保留期限和删除路径。

### 11.2 测试与质量

- 新功能至少覆盖正常路径、权限拒绝、边界输入、并发和失败恢复。
- 文件系统、数据库和网络功能优先使用真实临时环境测试，而不是只模拟成功结果。
- 每个生产事故补充可重复的回归测试和部署检查。
- Windows 是当前正式支持平台，构建和发布验收以 Windows 10/11 x64 为准。

### 11.3 体验、一致性与无障碍

- 所有新增用户文案同步五种语言，不以硬编码英文作为失败兜底。
- 键盘操作、焦点管理、对比度、动态效果开关和屏幕阅读器语义逐步纳入验收。
- 长任务始终展示阶段、进度、取消能力和失败后的下一步。
- 客户端、管理端和官网对同一版本、角色和状态使用一致术语。

### 11.4 文档

- 路线图只记录未来方向，当前事实写入 README、API、数据模型和部署文档。
- 接口或配置变化必须同步示例、类型、测试和部署说明。
- 已完成事项从路线图移除并进入版本记录，避免长期保留“永久完成列表”。

## 十二、长期研究方向

以下方向有价值，但尚不足以进入承诺阶段：

- MOD 包格式、依赖关系、启用顺序和冲突检测。
- 手柄映射、振动、死区和每游戏配置。
- mDNS 或其他去中心化房间发现方式。
- 内容寻址缓存、跨市场去重和可验证发布元数据。
- GitHub Gist、WebDAV 或用户自有存储上的可选存档同步。
- macOS/Linux 客户端与跨平台游戏包规范。
- 跨市场全局游戏身份和创作者身份映射。
- 更完整的高对比度、色觉辅助和辅助技术支持。

这些方向进入实施前，必须先回答：是否强化本地优先、是否有明确用户路径、是否可维护、是否有安全边界、在线依赖失效时如何降级。

## 十三、明确不做或暂不做

- 不把登录扩展为本地游戏库、启动、成就和统计的强制条件。
- 不把官方 Relay 变成联机的唯一入口。
- 不引入启动时在线授权、平台 DRM 或远程撤销本地游戏的能力。
- 不在近期引入真实货币交易、创作者分成、可交易 BZ 币或玩家投机市场。
- 不在内容治理成熟前开放陌生人私信、群聊和无限离线消息。
- 不为每个页面复制独立的评论、点赞、举报和审核数据模型。
- 不因为功能增加就提前拆分微服务；先保持清晰模块边界和可测试性。
- 不在缺少备份、验证和回滚方案时直接修改生产数据结构。
- 不将 macOS/Linux 构建脚本等同于正式支持承诺。

## 十四、版本决策与交付门槛

### 14.1 进入开发前

每个较大功能必须先写清楚：

1. 解决的用户问题和不解决的问题。
2. 本地、主进程、Relay、数据库、管理端分别承担什么职责。
3. 登录、所有权、权限、限流和隐私边界。
4. 在线依赖失败后的降级行为。
5. 数据结构、迁移、备份、恢复和删除策略。
6. 可观察结果和验收测试。

### 14.2 合并前

- 客户端类型检查、相关单元测试和生产构建通过。
- Relay 全量测试、配置示例检查和接口契约检查通过。
- 管理端类型检查与生产构建通过。
- 新增文案完成五种语言同步。
- 安全敏感路径经过失败场景和越权场景验证。

### 14.3 发布前

- 在与生产一致的环境完成依赖安装和全量测试。
- 数据库变化已独立审核、备份并执行验证查询。
- 部署过程具备健康检查和自动或明确的人工回滚步骤。
- 桌面安装包完成文件头、大小、SHA-256、版本和下载验证。
- 发布后验证本地核心路径、在线关键路径和降级路径。
- 全部验证通过后再删除部署备份。
