# BZ-Games 平台路线图

最后更新：2026-08-20

本文以当前代码和已部署的服务为准。已完成的能力不再列入“未来计划”；未实现的功能明确标注为计划，避免把设想当成现状。

## 平台定位

BZ-Games 是一个本地优先的 Windows 游戏平台：游戏库、游戏运行、联机、成就、统计和大部分设置都在客户端完成。Relay Server 和管理端提供登录、同步、联机中继、市场托管、反馈和运维等在线能力，在线服务不可用时不应阻断本地游戏的安装管理、启动和游玩。

当前桌面端版本：`3.2.2`

当前主要组成：

- Electron + Vue 3 + TypeScript 桌面客户端
- 独立 Node.js Relay Server
- Vue 3 管理端
- GitHub OAuth 作为统一在线身份入口
- 客户端加密 SQLite、服务端 MySQL 与 MongoDB 存储

## 当前已完成能力

### 桌面客户端

**游戏库**

- 本地导入已有游戏目录，支持带 `game.json` 的标准导入和手动创建清单
- 游戏多版本安装、切换、删除、收藏、拖拽排序
- 多游戏存储路径、默认库迁移和数据健康检查
- 卡片布局、图标布局和 Steam 风格布局
- 卡片和图标网格会根据窗口宽度自动均分，并保留最小视觉尺寸
- 游戏封面、图标、视频、成就图标读取与本地缓存
- 游戏清单透明加密保存
- 游戏版本来源追踪：
  - `install_source = manual`、`market_id = NULL`：手动导入或无法确认来源的版本
  - `install_source = market`、`market_id` 非空：从市场安装的版本
- 旧版客户端升级时自动补充来源字段，历史版本回填为手动来源

**游戏市场**

- 市场目录 + 市场索引的两级结构
- 官方市场、GitHub Release 市场和第三方市场源
- 市场源搜索、市场详情、版本选择和平台版本兼容检查
- ZIP / 7z 下载、大小校验、SHA-256 校验、解压和安装
- 下载队列、暂停、恢复、取消、断点续传和中断任务恢复
- 下载浮球与任务进度通知
- 市场资源、封面和图标缓存
- 市场源 ID 校验，防止目录与索引错配
- 市场详情可跳转游戏托管入口

**游戏运行与 Game API**

- URL、原生程序、HTML 和本地服务等启动模式
- Game API V1 JSON 协议和 V2 二进制帧协议
- 消息收发、广播、订阅、环境变量注入
- 游戏运行时统计上报、成就解锁和会话记录
- 游戏窗口、启动失败、进程结束和房间联动处理

**游戏生涯**

- “游戏统计”和“成就”已合并为“游戏生涯”
- 统计与成就使用两个内部 Tab，交互样式与房间发现页一致
- 游玩时长、会话记录、日历热力图、版本统计
- 热力图 PNG 分享
- 成就列表、版本筛选、完成进度、解锁时间和新成就提醒

**联机房间与聊天**

- 创建、加入、准备、开始、离开、踢人、房间密码和断线重连
- 局域网、虚拟局域网和 Relay 服务器三种发现/连接路径
- Relay 房间中继、短地址和延迟检测
- 房间内文字、语音、图片消息
- 聊天独立弹窗和历史记录
- 敏感词过滤与房间权限控制

**账户、同步与个性化**

- GitHub OAuth 登录、会话过期和失效处理
- 云端同步设置、用户数据、SQLite 业务数据和游玩记录
- 本地优先的数据恢复与同步限制
- 头像、头像框、昵称样式、昵称特效、主题、语言和托盘行为设置
- BZ 币、每日签到、游玩时长奖励、头像框解锁与装备
- 简体中文、繁体中文、English、日本語、文言文、Deutsch

**反馈与更新**

- 建言献策仅对已登录用户开放
- 文本、图片反馈、服务端反馈历史、官方回复和状态查看
- 自动更新、下载、校验、安装和更新状态通知
- 更新缓存清理、下载包管理和失败状态提示
- 开发模式下 GitHub OAuth 回调可正常返回客户端

### Relay Server

- WebSocket 房间中继、房间发现、心跳、人数和资源限制
- GitHub OAuth、用户、角色、会话和会话过期清理
- 云端快照上传、下载和同步限流
- 登录用户反馈提交、图片存储、用户查看和管理员处理
- 游戏托管：游戏元数据、版本、安装包、封面和图标上传、审核、发布、更新和删除
- 平台版本发布下载服务
- 服务端系统监控和实时网络带宽指标
- 敏感词服务和房间消息过滤
- MySQL 保存身份、会话、云端元数据、反馈、托管游戏和审核数据
- MongoDB 保存反馈图片及需要对象存储的数据
- 服务端结构通过启动初始化创建，生产环境已部署并受管理端 RBAC 保护

### 管理端

- GitHub OAuth 管理员登录和 RBAC 权限控制
- 欢迎页、反馈审核、用户列表、游戏托管、平台版本和系统监控
- 平台版本上传有两条入口：GitHub Actions 自动同步和超级管理员手动上传
- 超级管理员手动上传允许发布低于当前版本号的版本
- 游戏托管支持元数据、版本、安装包、封面和图标的审核流程
- 反馈查看、回复、状态修改、图片查看和删除
- CPU、内存、磁盘、网络带宽、房间、连接数和运行时长监控

## 当前数据与安全边界

### 客户端本地数据

客户端使用加密 SQLite 保存：

- 游戏与游戏版本
- 版本路径、安装时间、安装来源和市场 ID
- 收藏、排序、游玩会话、统计上报和成就解锁

`install_source` 和 `market_id` 是本地来源记录，主要用于客户端功能门控和用户可见信息。它们不是服务端可信凭证，因为本地数据理论上可以被修改。

### 在线身份

- 服务端以 GitHub 会话和服务端用户 ID 识别用户，不信任客户端提交的用户名或用户 ID
- 客户端渲染进程不应直接持有或拼装敏感认证逻辑，在线请求通过主进程服务完成
- 本地功能不要求登录；反馈、云同步和未来的在线社区功能要求登录

### 市场来源与评论前置条件

未来评论功能必须同时处理两个问题：

1. 客户端只有在已登录且本地版本来源为市场时显示发布入口。
2. 服务端必须验证 GitHub 会话以及市场中的游戏版本是否真实存在，不能仅相信客户端传入的来源字段。

不同市场可能出现相同游戏 ID，因此在线评论的完整作用域应使用 `market_id + game_id + game_version`。如果未来确定所有市场共享全局唯一游戏 ID，再评估是否简化为游戏 ID + 版本。

## 近期优先级

近期目标是巩固已经上线的本地库、市场、登录和托管链路，再增加依赖这些基础能力的在线功能。

### P0：可靠性和维护性

- 完成客户端数据库来源字段在更多真实旧库上的升级验证
- 增加市场安装、手动导入、任务恢复和来源写入的自动化测试
- 增加 Relay Server 初始化结构、权限和数据清理测试
- 完善服务端数据库备份、恢复、索引检查和故障告警
- 对云同步、反馈、市场托管和平台更新接口统一错误码、超时和重试策略
- 继续保持在线服务故障不影响本地游戏库和游戏启动

### P1：市场游戏评论

评论是当前最明确的下一项产品功能，建议先做小而完整的首版：

- Relay Server 现有 MySQL 增加评论表，不另建独立物理数据库
- 评论至少保存评论 ID、`market_id`、`game_id`、`game_version`、服务端 `user_id`、GitHub 登录名快照、正文、状态、创建时间和更新时间
- 以 `market_id + game_id + game_version` 建立查询索引和唯一作用域
- 列表接口采用游标分页和稳定时间排序
- 登录后才能发布、编辑和删除；普通用户只能管理自己的评论
- 限制正文长度、提交频率和单用户评论数量，支持隐藏、删除和管理员审核
- 客户端市场详情页显示评论列表和发布入口；手动导入版本只允许浏览
- 评论服务通过客户端主进程和 IPC 调用，渲染进程不直接持有登录令牌
- 评论读取失败时只隐藏评论区域，不影响市场浏览和安装
- 管理端增加评论检索、隐藏、删除和用户维度审核

### P1：市场体验完善

- 市场版本更新日志和变更说明
- 更清晰的安装来源、已安装版本和版本更新提示
- 下载队列并发策略和资源占用提示
- 缓存清理结果、失败任务恢复和磁盘空间提示
- 市场索引、托管版本和下载资源的一致性检查

### P1：管理和运维

- 平台发布、游戏托管、反馈和评论审核统一审计日志
- 管理端批量操作、筛选、分页和危险操作二次确认
- 服务端健康检查覆盖 MySQL、MongoDB、对象存储和关键外部依赖
- 生产部署脚本增加版本回滚、配置校验和服务启动后验证

## 中期计划

### 社交能力

在评论稳定后，再考虑建立更完整的社交关系：

- 好友列表和备注
- 基于局域网的好友发现
- 基于 Relay 的在线状态和好友邀请
- 从好友列表快捷邀请进入房间
- 明确离线消息保存期限和隐私策略

当前房间聊天不等于好友系统，好友关系、在线状态和离线消息仍未实现。

### 创作者与市场生态

- 游戏托管发布流程继续完善，增加发布者统计和版本变更记录
- 市场源贡献校验、自动化索引检查和重复游戏 ID 检查
- 创作者使用的 `game.json` 编辑和校验工具
- Game API 调试工具和本地打包检查
- 受控的评分、举报和评论审核体系

### 本地内容能力

- 游戏截图管理和按游戏分组
- 游戏存档备份、恢复和版本化管理
- 可选的成就解锁截图
- 更细粒度的游戏设置、启动参数和环境变量管理

## 长期方向

以下方向尚未进入实现阶段，排在本地稳定性、评论、市场和管理能力之后：

- MOD 包格式、启用/禁用、排序和冲突检查
- GitHub Gist 或其他可选存档云同步
- macOS / Linux 客户端
- 手柄映射、振动和死区配置
- mDNS 等去中心化房间发现
- 高对比度、色盲友好配色和屏幕阅读器支持
- 更完整的跨市场身份和游戏唯一性规范

## 明确不作为近期目标

- 不把登录强制扩展到本地游戏库、游戏启动、单机成就和本地统计
- 不把 Relay Server 变成本地游戏运行的必需依赖
- 不依赖客户端上报的用户名、用户 ID 或来源字段进行服务端授权
- 不在评论首版同时引入点赞、楼中楼、悬赏、私信等复杂社交功能
- 不在没有迁移、备份和回滚方案前直接变更生产数据库结构

## 版本交付原则

1. 新功能先完成客户端、服务端、管理端和权限边界设计，再实现界面。
2. 数据库变更必须包含初始化结构、旧数据迁移、失败恢复和自动化验证。
3. 所有在线接口必须验证服务端会话和资源归属，客户端字段只能作为提示或功能门控。
4. 在线功能失败时保持本地功能可用，并提供可理解的错误信息。
5. 发布前至少通过客户端类型检查与构建、数据库迁移测试、服务端接口测试和管理端构建。
