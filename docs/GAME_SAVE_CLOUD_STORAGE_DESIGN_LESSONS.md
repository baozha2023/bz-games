# 游戏存档云存储设计经验

本文记录已退役的 Platform Cloud Snapshot 在 MySQL 与 MongoDB GridFS 联动、
流式传输和生产清理方面的经验。它不是现有功能说明，也不保留任何可调用的
云快照接口、客户端入口或兼容实现；未来的游戏存档云存储必须重新定义独立的
领域模型和协议。

## 1. 适合复用的总体思路

大对象本体与强一致元数据应分开存放：GridFS 保存不可变二进制对象，MySQL
保存用户、游戏、存档槽位、对象版本、哈希和当前指针。上传先产生一个不可变
候选对象，校验成功后才在 MySQL 事务内切换指针。读取始终先获取一次已发布
指针，再按精确对象 ID 下载，不能靠文件名或 `metadata.kind` 猜测“最新版”。

推荐状态流如下：

```text
接收上传流 → 写入候选 GridFS 对象 → 流式校验大小/哈希/格式
          → MySQL 行锁与事务发布新指针 → 返回成功
          → 延迟回收旧对象
```

发布前失败必须删除候选对象并释放限流预留；发布后响应失败不能回滚已提交的
指针，而应让客户端通过幂等查询确认结果。旧对象只能在事务提交之后回收，且
需要宽限期，避免正在进行的下载被立即截断。

## 2. 一致性边界

- GridFS 对象一经写入不得原地修改。内容变化必须生成新对象 ID。
- MySQL 指针切换和“本次操作成功消耗额度”应在同一事务提交。
- 并发上传必须对同一 `user + game + slot` 指针行加锁，并递增服务端版本。
- 客户端版本号不能直接作为最终排序依据；服务端发布序号才是权威顺序。
- 对象必须保存 SHA-256、字节数、内容类型和协议版本，下载时返回同一组元数据。
- 数据库无法与 MongoDB 做单一 ACID 事务，因此要按 Saga 思路补偿候选对象，
  并通过后台孤儿扫描处理进程崩溃留下的无指针对象。

## 3. 流式处理与资源上限

不要将完整存档读入 Node.js 堆内存。请求体应直接经过计数、哈希和格式校验流
写入 GridFS；同时强制要求可验证的大小上限，并在实际流量超过上限时主动中断。
下载同样使用流式管道，只有响应完整结束后才提交下载成功状态。

仅检查 `Content-Length` 不够：分块传输、伪造头部和中途断开都必须由实际字节
计数覆盖。对压缩包还需限制解压后总字节数、文件数、单文件大小和路径深度，
拒绝绝对路径、`..`、符号链接及大小写碰撞。

## 4. 领域模型必须独立

未来游戏存档不能复用平台配置备份或数据库备份。至少应明确：

- 游戏稳定 ID、存档槽位 ID、设备 ID、服务端发布版本和父版本；
- 游戏版本、存档格式版本、平台、文件清单与每个文件的哈希；
- 手动存档、自动存档、冲突副本和删除墓碑的生命周期；
- 配额、保留版本数、冲突策略以及用户可见的恢复点；
- 端到端加密边界、密钥归属和丢失密钥后的行为。

默认不应以“最后写入覆盖”为冲突策略。客户端上传应携带其读取到的父版本，
服务端用 compare-and-swap 发布；父版本落后时生成冲突结果，不静默覆盖另一台
设备的新存档。

## 5. GridFS 多业务隔离

共享 bucket 时，`metadata.kind` 只是分类条件，不是所有权证明。业务表必须保存
精确对象 ID，删除时优先按指针或关联表枚举 ID。批量运维必须同时满足精确
`metadata.kind` 与预期 ID 集合，并在删除前记录文件、分块、大小和哈希清单。

反馈图片、论坛图片与未来游戏存档应使用不同 kind。禁止清空整个 `files` 或
`chunks` collection；删除文件必须通过 GridFS bucket 的 delete 操作，确保对应
chunks 一并删除。

## 6. 限流与失败语义

长耗时上传适合“预留—提交—释放”三阶段限流。预留包含随机 token 和租约到期
时间；校验、存储或发布失败时释放，只有成功发布才提交冷却时间。进程崩溃后，
过期租约必须可由新请求接管。上传与下载是否共用额度要在产品层明确，不能只靠
URL 拼接 endpoint key。

错误码应区分认证失效、冲突、配额不足、对象缺失、校验失败、限流和服务不可用。
只有稳定的会话过期/失效错误可以清除客户端登录态；网络错误和服务端 5xx 不得
导致本地凭据丢失。

## 7. 生产变更与清理经验

涉及 MySQL 指针和 GridFS 对象的清理应遵循固定顺序：

1. 停止相关写入口，并确认没有进行中的上传。
2. 只读盘点目标 MySQL 表、目标限流 key、目标 GridFS kind 及受保护 kind。
3. 创建权限为 `0700/0600` 的临时备份，记录对象字节数和 SHA-256，并复验备份。
4. 按清单通过 GridFS API 删除精确对象，再删除 MySQL 指针表和专属限流记录。
5. 部署不再创建表、不再注册路由的新代码并重启服务。
6. 验证旧路由为普通 `404`、目标表不存在、目标对象与孤儿 chunks 均为零。
7. 对反馈、论坛等受保护对象重新计算数量、大小和哈希，确认完全未变。
8. 全量测试与生产健康检查通过后删除临时备份，并验证备份路径不存在。

备份目录、清理状态文件和传输包都属于敏感运维材料，不应提交仓库或长期留在
服务器。清理脚本必须验证目标绝对路径和真实路径，禁止接受 `/`、`~`、父目录
跳转或未解析的通配符。

## 8. 本次退役边界

V4 不提供 Platform Cloud Snapshot。客户端仅保留 GitHub 账号登录、退出、昵称
同步与在线状态；V2 本地备份及 V1 导入都不会导出或导入账号会话、账号身份和
GitHub Token。服务端不注册任何平台快照路由，也不初始化平台快照指针表。

生产退役的最终数量、受保护对象指纹和临时备份删除结果，应以实际部署验收记录
为准，不在设计文档中预写成功结论。
